# サブエージェント並列翻訳ワークフロー(Claude Code 向け)

未翻訳エントリーのある `.po` を、**下訳の生成だけ**サブエージェントに並列で任せ、書き込みはメインが直列で行うためのオーケストレーション手順書。SKILL.md「Claude Code でサブエージェントに下訳を分担させる場合」の詳細。

**対象環境**: Claude Code のように Agent ツールでサブエージェントを起動できる環境。使えない環境(Claude.ai など)では `contribution-workflow.md` 1.1 の直列ループで進める。スクリプト自体は環境を問わず使える(1.4)。

このワークフローは Skill の標準ワークフロー(SKILL.md / `contribution-workflow.md`)を前提とし、その安全装置を一切弱めない。並列化して速くなるのは下訳までで、**人間レビューと手動 Import の義務はそのまま**。未精査の大量投入は提案の一括拒否につながる。

## 1. 基本原則と絶対に守ること

| フェーズ | 並列化 | 理由 |
|---|---|---|
| ① 準備(訳語リスト作成) | しない(メインのみ) | 訳語統一の基準を 1 か所で確定させるため |
| ② 下訳生成 | **する**(サブエージェント × N) | チャンクごとに別 JSON ファイルへ書き込むので競合しない |
| ③ 適用(apply → validate) | **しない**(メインで直列) | インデックス再採番によるズレ・競合を防ぐため |
| ④ 人間レビュー → Import | しない(人間が手動) | ハンドブック明記の機械翻訳精査義務。省略不可 |

絶対に守ること:

- **サブエージェントに `.po` を書き込ませない**。書き込みを許可するのは**メインが指示した下訳 JSON のパス 1 つだけ**(チャンクごとに別パスを指定する)
- **サブエージェントに `apply_translations.py` のインデックスを渡さない**。あのインデックスは呼び出しごとに未翻訳エントリーへ 0 から振り直されるため、生成と適用の間に時間差があると必ずズレる。チャンク内の番号 `n`(`### N`)は別物で、`po_collect.py` が `chunks/chunk_NN.json` で msgid に戻す。適用時のインデックスはメインが直前の `--list` で毎回引き直す
- **サブエージェントに `.po` を読ませない・Grep させない**。既存訳の見本は `po_chunk.py` がチャンクに `ref:` 行として添付する。`.po` を Grep しに行かせると 1 本の所要が数倍になる
- **書き込み → validate のループは 1 本の直列パイプライン**のまま維持する。`.po` の書き戻しを自前で実装せず、必ず `apply_translations.py` を呼ぶ(自前の書き戻しは改行の二重化で `.po` を壊す)
- 完了しても「これで完成」と断定しない。人間レビューと手動 Import が残っていることを最後に必ず伝える

## 2. 補助スクリプトと作業ディレクトリ

| スクリプト | フェーズ | 役割 |
|---|---|---|
| `scripts/po_chunk.py` | ①→② | 未翻訳の抽出・種別分類・頻出語・チャンク分割・既存訳の見本と Project Glossary の添付・番号 → msgid 対応表 |
| `scripts/po_collect.py` | ② | 下訳 JSON の回収・ドラフト段階の機械チェック・訳文プール作成・rework チャンク生成 |
| `scripts/po_apply_loop.py` | ③ | 未翻訳一覧の取り直し(`--list` と同じ判定)→ apply → validate の直列ループ |

3 本とも SKILL.md と同じディレクトリ配下の `scripts/` にある(Claude Code の標準配置なら `~/.claude/skills/wordpress-ja-translation-guide/scripts/`)。役割・終了コード・下訳 JSON の形式・機械チェックの根拠は `contribution-workflow.md` 1.4 にまとめてあり、ここでは繰り返さない。

作業ディレクトリは翻訳対象プロジェクト側に `.work/{slug}/` のように作る。UI と readme で分け(`.work/{slug}-ui` / `.work/{slug}-readme`)、同じファイルの 2 回目以降は日付などを付けて別にする。`drafts/` にドラフトが残る作業ディレクトリでは `po_chunk.py` が止まる(番号と msgid の対応が変わり、古いドラフトが別の msgid に付くため)ので、毎回新しい `--outdir` にするか `--force` で前世代を退避する。中間成果物をコミットするかどうかはプロジェクトの方針に従う(人間が下訳を直接レビューできる証跡になる)。

## 3. フェーズ①: 準備(メインのみ)

数千件規模では表記ゆれ対策がすべて。分担を始める前に必ずやる。件数が少なくても手順 4 の確認まで省かない。

1. **チャンク分割と頻出語の抽出**

   ```bash
   python ~/.claude/skills/wordpress-ja-translation-guide/scripts/po_chunk.py path/to/ja.po --outdir .work/{slug} --ref path/to/core-ja-translated.po
   ```

   `entries.json`(msgid・種別・`gp-priority`・ロケーション)、`wordfreq.txt`(頻出英単語)、`chunks/chunk_NN.md`(サブエージェントに渡す)、`chunks/chunk_NN.json`(番号 → msgid。回収用。サブエージェントには渡さない)を出力する。未翻訳の判定は `apply_translations.py` と同じなので `--list` と完全に一致する。

   - `--ref` には既存訳の見本を引く翻訳済み `.po` を渡す(複数可)。同じディレクトリの `*-translated.po` と対象 `.po` 自身の翻訳済み分は指定しなくても拾う。コアの翻訳済み `.po` は `Cancel` / `Remove` のような共通ラベルの見本になるので、手元にあれば毎回足す。`*-glossary.csv`(GlotPress の Project Glossary エクスポート)があれば自動でチャンク末尾に付く
   - 既定は 1 チャンク = 30 件以下かつ msgid 合計 3,000 字以下(`--size` / `--max-chars`)。所要時間は件数と文字量の両方で決まり、1 本あたり固定費があるので、件数側は短い UI ラベル用、文字側は readme 用の上限として両方要る。種別ごとにまとめてから切る(`--no-group-by-kind` で無効化)。同種別が集まると語尾の指示が効く
   - `gp-priority: low`(changelog 等)が大半を占める場合は、**訳すか省くかをユーザーに確認する**(`--skip-low` で除外可)
   - 未翻訳件数・チャンク数・各チャンクの文字量と ref 件数・種別内訳を報告する。チャンクが 1 本しか立たなくてもそのまま進める(この方式の利点は並列だけではなく、`po_collect.py` の機械チェック・`ref:` 見本・作業ディレクトリに残る証跡・メインのコンテキスト温存にある)

2. **共通訳語リストを作る**。`wordfreq.txt` の上位語と原文中の製品名から、`.work/{slug}/translation-glossary.md` を `glossary-template.md` の型(固有名詞 / 一般訳語 / 文体 / プロジェクト固有の例外 / 既存訳見本 / `[要確認]` の 6 ブロック)で作る。[公式用語集](https://translate.wordpress.org/locale/ja/default/glossary)・`references/glossary.md`・[Consistency Tool](https://translate.wordpress.org/consistency) で確認が必要な語は `[要確認]` のまま確定させない。同じプロジェクトの前回のリストがあれば、それを土台にして差分だけ足す

3. 同じプロジェクトの別 `.po`(UI ↔ readme)に翻訳済みエントリーがあれば、文体・語尾の統一見本として訳語リストに添える

4. **ユーザーに訳語リストを提示し、進めてよいか確認する**。ここを飛ばすと数百件を訳し直すことになる

## 4. フェーズ②: 下訳生成(サブエージェント並列)

### 4.1. エージェント定義

下訳専用のサブエージェント定義を `assets/agents/po-draft-translator.md` として同梱している。Skill 単体ではエージェント定義を自動登録できないので、Claude Code で使うときは一度だけコピーする:

```bash
cp ~/.claude/skills/wordpress-ja-translation-guide/assets/agents/po-draft-translator.md ~/.claude/agents/
```

定義は `tools: Read, Grep, Glob, Write`(`.po` に書けない・apply を実行できない)、`model: sonnet`、`effort: medium`、`skills: [wordpress-ja-translation-guide]`(SKILL.md をプリロード)。役割の境界・読んでよいもの・種別タグと語尾・出力 JSON 形式・返答の形は定義が持つ。**呼び出し時のプロンプトで繰り返さない**(書き直すたびに抜けが出る)。

`effort` を `low` にしない。実測では共通訳語リストを読み飛ばし、リストの指定語を別の語に置き換えた。`medium` は継承(高い effort)より所要・出力トークンが大きく減り、劣化は機械チェックで拾える範囲に収まった。

定義が無い環境では `general-purpose` サブエージェントに `model: sonnet` で同じファイルを Read させて役割を指示してよいが、`tools` の制限と `effort` は効かない。「`.po` を書かない・読まない」をプロンプトで明示し、回収時の機械チェックで担保する。

### 4.2. 呼び出し方

各チャンクをサブエージェントに渡す。**Agent 呼び出しは 1 つの応答に全チャンク分をまとめて出す**(1 本ずつ別の応答で投げると直列になる)。同時実行数の上限を超える分は最初の波が返ってから次の波を出す。渡すものは 4 点だけ:

1. **チャンクファイルのパス**(`.work/{slug}/chunks/chunk_NN.md`)。msgid をプロンプト本文に貼らない
2. **共通訳語リストのパス**
3. **下訳 JSON の書き込み先パス**(`.work/{slug}/drafts/translations_NN.json`)。**チャンクごとに必ず別パス**を割り当て、既存ファイルのあるパスは再利用しない
4. プロジェクト固有の注意があれば 2〜3 行(製品名の扱い、画面の種類など)

「`.po` を読んで既存訳に揃えろ」とは書かない(見本は `ref:` 行として添付済み。書くと `.po` を Grep しに行く)。訳文本体はレスポンスに返させず、**JSON ファイルを正**とする。返答は書き込んだパス・件数・`[要確認]` 件数の要約だけにする。

同時本数が多いとストールすることがある(Read を終えて訳文を書き始める前に止まり、出力トークンが数百のまま失敗する)。まず全チャンクを 1 波で出し、ストールしたら 2 本ずつ投げ直す。ストールしたチャンクは書き込み先が空のままなので同じパスで再投入できる。

### 4.3. チャンクファイルの形式

`po_chunk.py` が出すチャンクは 1 エントリーがこの形:

```
### 12 [description paragraph]
<<<MSGID
原文(改行を含むことがある。行頭のタブやスペースも原文の一部)
>>>MSGID
<<<MSGID_PLURAL
複数形の原文(あるときだけ)
>>>MSGID_PLURAL
msgctxt: 同じ原文を文脈で区別するための語(あるときだけ)
translators: 変数の意味の説明(あるときだけ)
location: ソースファイルのパス(文脈のヒント。訳文には含めない)
ref [same-plugin]: "既存の原文" → "既存の訳文"
ref [core-ja-translated.po]: "既存の原文" → "既存の訳文"
previous: "前回の下訳"(再翻訳チャンクのときだけ)
reason: 前回の下訳が機械チェックで弾かれた理由(再翻訳チャンクのときだけ)
```

`<<<MSGID` / `>>>MSGID` の区切りは改行入り msgid を事故なく渡すための要(1 行 1 件の形式だと複数行の msgid で境界が壊れる)。`ref:` の `[same-plugin]` は同じプロジェクトの承認済み訳で、製品固有のラベル・機能名はこれに揃える。ラベル末尾の `~case` は大小文字・前後空白違いの近似一致、`~ctxt` は msgctxt が違うエントリーの訳で、どちらも参考に留める。チャンク末尾に `## Project Glossary` があれば `*-glossary.csv` の内容で、共通訳語リストより強い。

### 4.4. 回収時のチェック(メイン)

```bash
python ~/.claude/skills/wordpress-ja-translation-guide/scripts/po_collect.py --outdir .work/{slug}
```

番号キーを msgid に戻し、件数・未回収を検証し、機械チェック(`contribution-workflow.md` 1.4 の表)を通して `pool.json` / `hold.json` / `manual.json` / `missing.json` / `rework.json` に分ける。終了コードで次の動きが決まる:

| 終了コード | 意味 | 次にやること |
|---|---|---|
| 4 | ドラフトの形式エラー(壊れた JSON・未知の msgid・範囲外の `n`) | `collect-report.txt` を見て直してから再実行 |
| 2 | 未回収がある | `missing.json` を見て、該当する**元のチャンク**(`chunks/chunk_NN.md`)をそのまま再投入する。書き込み先は `drafts/translations_NN_2.json`(以降 `_3`, `_4` …)。**`NN` は元のチャンク番号のまま**にする(番号キーの復元に `chunks/chunk_NN.json` を使うので、番号を変えると対応表が引けず全件が形式エラーになる)。同じ番号は後のファイルの訳文で上書きされるので、足りない番号だけ入っていればよい |
| 3 | 機械チェック NG(rework)がある | `chunks/rework_NN.md`(前回の下訳と理由付き)が生成されているので、通常のチャンクと同じ手順で投げる(書き込み先は `drafts/translations_rework_NN.json`)。戻ったら `po_collect.py` を再実行する(通った訳文は元の通常ドラフトに書き戻され、rework ドラフトは `drafts/consumed/` へ移る)。2 回回しても消えないものは `rework.json` の理由を見てメインが直接判断する |
| 0 | 問題なし | フェーズ③へ |

`[要確認]` 付きは `hold.json` に分離され、適用対象から外れる(人間判断に回す)。msgctxt 違いで同じ msgid が複数あるエントリーは `manual.json` に集まり pool には入らない(フェーズ④で 1 件ずつ手動適用)。

## 5. フェーズ③: 適用(メインで直列)

```bash
python ~/.claude/skills/wordpress-ja-translation-guide/scripts/po_apply_loop.py path/to/ja.po --outdir .work/{slug}
```

**並列化禁止**。ループは未翻訳一覧の取り直し(`--list` と同じ判定)→ msgid 照合付き JSON 20 件 → apply → `validate_po.py --errors-only`。`[ERROR]` が出たら中断する(終了コード 2)。書き込めなかったエントリーは `blocked.json` に落ちて次バッチから外れる(放置するとループが空転する)。msgctxt 違いで同じ msgid が複数あるエントリーは `manual.json` と同じ扱いで送らず、末尾に一覧が出る。apply が 1 件も書けなかったとき(読み取り専用など)は `blocked.json` に入れずに終了コード 2 で止まる。

`blocked.json` に残ったものは未翻訳のまま。原文に `100% free` のような裸の `%` があると `% f` がプレースホルダーとして誤検出され、構造上書き込めない。訳案を添えて人間に渡す。

手でやる場合も同じループ(`contribution-workflow.md` 1.1 の運用ルール)。`--errors-only` の判定は行頭 `[ERROR` で見ること。集計行(`0 ERROR / 39 WARN`)に "ERROR" の文字列が含まれるので、単純な部分一致だと WARN しか無い状態でも誤って中断する。

## 6. フェーズ④: 仕上げと報告

1. **最終フルチェック**: `validate_po.py` をオプションなしで全件実行する。ERROR が残った状態で Import はしない。WARN は目視判断のうえ修正する(プロジェクトとして方針が決まっているルールは `--ignore` で除外してよい。`contribution-workflow.md` 1.2)
2. **表記ゆれの通し確認**(validate では拾えない)。msgstr 行に絞って grep する:
   - 訳語の対立ペア(訳語リストで決めた語の反対側。`統合` ↔ `連携`、`エクスポート` ↔ `書き出し` など)
   - 全角記号 `[！？（）：；]`
   - 同義語のゆれ(同じ原語が 2 表記に分裂していないか)、カタカナ長音の有無
   - 常体の混入(本文が `〜である` `〜する。` で終わっていないか)
   - 数量表現(一般の数量は詰め、バージョン番号・HTTP ステータスコードは方針に従う)
   - 数値が入る `%s` の前後スペース(`translators:` が無い・数値と読めないものは `PH_NUM_SPACE` が判定しないので目視)
   - JS で連結される断片(原文が文の途中で切れている・末尾が `:` やスペースのエントリー)は、前後のエントリーと件数を挟んで連結した日本語を組み立てて読む。下訳が `[要確認]` を付けないことがある
3. `grep -n msgid_plural path/to/ja.po` で複数形の取りこぼしを確認する
4. **`[要確認]` プールの解消**: `hold.json` / `manual.json` / `blocked.json` のエントリーを用語集・Consistency Tool・翻訳コミュニティへの相談で確定する。確定したら `pool.json` を差し替えて `po_apply_loop.py` を再実行すればよい(`blocked.json` は消してから)
5. 以下をユーザーに報告して終了する:
   - 翻訳完了件数と validate 結果(残 WARN の一覧と、それを残した理由)
   - `hold.json` / `manual.json` / `blocked.json` の一覧
   - 自分の判断で直した箇所(訳語統一・表記修正)
   - **残作業: 人間による目視レビュー → 手動で Import Translations からアップロード。無人アップロードはしない**

## 7. トラブルシューティング

| 症状 | 原因 | 対処 |
|---|---|---|
| apply 時に WARN「msgid が現在のリストと一致しません」が頻発 | `--list` の取り直し漏れ、または複数バッチ分の JSON を事前にまとめて作っている | バッチ直前の `--list` 取り直しを徹底する。msgid 照合が自動再解決してくれるが、WARN 前提の運用にしない |
| 「msgid が複数の未翻訳エントリーに一致」エラー | msgctxt 違いの同一 msgid | `po_collect.py` が `manual.json` に分けるのでループには流れない。`--list` の個別インデックスを `location` で見分けて 1 件ずつ手動適用 |
| サブエージェント間で訳語がバラバラ | 共通訳語リストの未配布・不徹底 | フェーズ①に戻って訳語リストを拡充し、以降のチャンクに反映。適用済み分はフェーズ④で修正 |
| `PH_MISMATCH` が多発 | サブエージェントの出力前セルフチェック不足 | `po_collect.py` が `rework.json` に落として `chunks/rework_NN.md` を作るので、それをそのまま投げ直す。プロンプトや定義に強調を足さない。2 回回しても残るものはメインが `reason` を見て直す |
| 適用ループが同じ件数のまま進まない | 書き込めないエントリーが未翻訳のまま先頭に居座っている | `po_apply_loop.py` が `blocked.json` に落として次バッチから外す(自動) |
| validate が WARN しか無いのに中断する | `--errors-only` の判定を "ERROR" の部分一致でやっている | 集計行に引っかかっている。行頭 `[ERROR` で判定する |
| サブエージェント 1 本が何分もかかる | `.po` を Grep して既存訳を探している | エージェント定義の「読まないもの」を確認。プロンプトに「既存訳に揃えろ」と書かない。見本はチャンクの `ref:` 行にある |
| サブエージェントが直列にしか走らない | Agent 呼び出しを 1 本ずつ別の応答で出している | 1 つの応答に全チャンク分の Agent 呼び出しをまとめる |
